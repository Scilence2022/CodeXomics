01 系统概述与设计哲学

CodeXomics MCP Bridge 是一个精心设计的「双向桥接」系统，解决了桌面基因组分析应用与外部 AI 代理之间的互操作性难题。其核心挑战在于：

  • 渲染进程依赖：大部分基因组操作（导航、序列提取、轨道渲染等）必须运行在 Electron 渲染进程内，因为它们直接操作 DOM 和 Canvas
  • 外部协议标准：MCP 客户端（如 Claude Desktop、Cursor）遵循标准 MCP 协议，需要通过 SSE/WebSocket 等标准传输层通信
  • 多客户端并发：需要同时支持内部聊天 AI、外部 MCP 客户端、以及远程桥接客户端的并发工具调用

Bridge 的设计哲学是：将 MCP 协议适配层与业务逻辑完全分离，通过「请求-响应」的异步管道桥接两个进程世界。

3.1 StandardClaudeMCPServer（主进程 MCP 服务器）

职责定位
  • 实现 MCP 协议规范的「服务端」
  • 管理 HTTP/SSE/WS 三种传输层
  • 路由工具调用到正确的执行层
  • 管理多窗口客户端注册与路由
技术实现
  • 基于 @modelcontextprotocol/sdk 构建
  • Express 处理 HTTP/SSE 端点
  • ws 库处理 WebSocket 连接
  • 支持 tools / agent 双模式
  • 端口：HTTP :3002 / WS :3003
// 服务器初始化关键代码 this.mcpServer = new Server( { name: 'codexomics', version: '1.0.0' }, { capabilities: { tools: { listChanged: true }, logging: {} } } ); // 注册 MCP 协议处理器 this.mcpServer.setRequestHandler(CallToolRequestSchema, async req => { ... }); this.mcpServer.setRequestHandler(ListToolsRequestSchema, async req => { ... });

3.2 MCPBridge（渲染进程 WebSocket 客户端）

职责定位
  • 渲染进程→主进程 MCP 服务器的通信桥梁
  • 自动连接 + 指数退避重连
  • 接收工具执行请求并委派给 InternalMCPServer
  • 上报窗口 ID 和基因组加载状态
连接策略
  • 基础间隔 5s，指数退避至最大 60s
  • 15s 心跳 ping 防止健康监控标记为 stale
  • 连接成功后发送 internal-client 身份标识
  • 支持 genome-loaded 事件上报
关键设计：为什么用 WebSocket 而不是 IPC？

MCPBridge 使用 WebSocket 而非 Electron IPC 连接主进程 MCP 服务器，原因是服务器可以作为独立进程运行（npm run codexomics-mcp-server），此时不存在 IPC 通道。WebSocket 方案在嵌入模式和独立模式下均能工作。

3.3 InternalMCPServer（渲染进程工具执行器）

双重入口架构
  • IPC 入口：监听 mcp-tool-call，处理来自 Electron IPC 的请求
  • WebSocket 入口：被 MCPBridge 委派，处理来自 WS 通道的请求
  • 两条路径最终都调用 executeMethod()
执行路由策略
  • 优先路径：委派给 ChatManager.executeToolWithPriority()（70+ 工具）
  • 降级路径：switch/case 回退处理器（20+ 方法）
  • 自动将 snake_case 工具名转换为 camelCase 方法名
// 方法名转换：snake_case → camelCase const toolName = method.replace(/([A-Z])/g, '_$1').toLowerCase(); // 优先委派给 ChatManager if (this.genomeStudio.chatManager) { const result = await this.genomeStudio.chatManager.executeToolWithPriority(toolName, parameters); } // 降级到直接处理器 switch (method) { case 'navigateToPosition': return await this.navigateToPosition(parameters); case 'codexomicsChat': return await this.handleCodexomicsChat(parameters); ... }

04 数据流全链路追踪

路径 A：MCP Client → SSE → Main Process → WS → Renderer（主路径）

Step 1
MCP Client 发起请求
客户端通过 SSE 传输层发送 tools/call JSON-RPC 请求
POST /sse { "method": "tools/call", "params": { "name": "navigate_to_position", "arguments": {...} } }
Step 2
MCP Server 接收并解析
CallToolRequestSchema handler 被触发，ToolsIntegrator.executeTool() 执行
this.toolsIntegrator.executeTool("navigate_to_position", args, clientId)
Step 3
ToolCategoryManager 分类验证
验证工具执行模式（server/client/hybrid），检查客户端连接可用性
this.toolCategoryManager.validateExecution(toolName, hasClient)
Step 4
委派到客户端执行
客户端依赖工具通过 WebSocket 或 IPC 发送到渲染进程
this.server.executeToolOnClient(toolName, parameters, clientId)
Step 5
MCPBridge 接收并委派
WebSocket 消息到达 MCPBridge，委派给 InternalMCPServer.executeMethod()
this.internalMCPServer.executeMethod(method, parameters)
Step 6
ChatManager 执行工具
优先通过 ChatManager.executeToolWithPriority() 执行，直接操作 DOM 和基因组数据
this.genomeStudio.chatManager.executeToolWithPriority(toolName, params)
Step 7
结果原路返回
结果通过 WS → MCP Server → SSE 返回 MCP Client，总延迟约 50-200ms
MCPBridge.sendResult() → MCP Server → SSE response

路径 B：MCP Client → SSE → Main Process → 就地执行（服务端工具）

Step 1-2
同上，请求到达 ToolsIntegrator
工具名为服务端工具（如 compute_gc、search_uniprot_database）
Step 3
服务端就地执行
直接在主进程 Node.js 环境中执行计算，无需客户端交互
return { gcContent: this.sequenceTools.calculateGCContent(sequence) }
Step 4
直接返回结果
跳过渲染进程往返，延迟极低（<10ms）

路径 C：Internal Chat → ChatManager（内部路径）

Internal
用户在 CodeXomics 内部聊天
内部 AI 通过 ChatManager.executeToolWithPriority() 直接执行工具，无需 MCP 桥接

06 多窗口支持

CodeXomics 支持同时打开多个基因组浏览器窗口，MCP Bridge 完整实现了多窗口路由机制：

窗口注册流程
  • main.js 创建 BrowserWindow 时分配 windowId
  • 通过 IPC 发送 windowId 到渲染进程
  • MCPBridge 收到后立即通过 WebSocket 上报
  • 主进程 MCP Server 维护 internalClients Map<windowId, ws>
工具路由策略
  • 指定窗口：工具参数包含 windowId，直接路由到对应 WS 客户端
  • 默认聚焦窗口：无 windowId 时，自动选择当前 focused 窗口
  • 窗口降级：聚焦窗口不可用时，回退到第一个可用窗口
// 多窗口路由核心逻辑 async executeViaInternalClient(toolName, parameters, clientId, targetWindowId) { let targetClient; if (targetWindowId && this.internalClients.has(targetWindowId)) { targetClient = this.internalClients.get(targetWindowId); // 精确路由 } else { targetClient = this.getFocusedWindowClient() || this.internalClient; // 默认聚焦 } targetClient.send(JSON.stringify({ type: 'tool-execution', ... })); }

多窗口数据结构

数据结构 位置 用途
windowRegistry main.js (权威) BrowserWindow 引用 + 基因组名
internalClients MCP Server windowId → WebSocket 映射
pendingRequests MCP Server requestId → Promise 映射
windowId MCPBridge 当前窗口标识

07 安全与认证体系

AuthenticationManager
  • API Key 认证：SHA-256 哈希存储
  • Session 管理：1 小时超时，可配置
  • Localhost 绕过：本地连接免认证（可配置关闭）
  • Master Key：管理级全权限密钥
  • Development Key：开发模式自动生成
传输层安全
  • SSE 端点：Bearer Token 认证中间件
  • WebSocket：首消息认证，10 秒超时
  • 内部客户端：仅允许 localhost 连接
  • Client Bridge：注册制 + Session 绑定
安全注意事项

当前 localhost 绕过默认开启（enableLocalBypass: true），且 WebSocket 内部客户端仅通过 IP 验证 localhost。在生产环境中，建议关闭 localhost 绕过并增加额外安全层。

08 连接健康监控

ConnectionHealthMonitor
  • Ping 间隔：30 秒
  • 超时阈值：60 秒无活动标记为 stale
  • 最大未响应 ping：3 次
  • 健康检查间隔：10 秒
  • 自动清理：2 倍超时阈值后强制移除
系统指标
  • 总连接数 / 断开数
  • 工具执行次数 / 错误率
  • 平均响应时间
  • 连接类型分布（SSE/WS/HTTP）
  • 系统状态：healthy / degraded / unhealthy

09 工具分类与执行路由

ToolCategoryManager 将 80+ 工具分为三类执行模式：

执行模式 说明 示例工具 数量
SERVER_ONLY 无需浏览器上下文，可在主进程直接执行 compute_gc, search_uniprot_database, translate_dna ~15
CLIENT_ONLY 必须运行在渲染进程，依赖 DOM/基因组数据 navigate_to_position, get_sequence, toggle_track ~30

11 架构优势与潜在改进

架构优势

灵活性
  • 三种通信路径（WS/IPC/Bridge）确保在不同部署模式下均可工作
  • 双模式（tools/agent）适应不同使用场景
  • 多协议外部服务器支持
健壮性
  • 指数退避重连机制
  • 心跳保活 + 健康监控
  • 超时保护（工具执行 30s/120s）
  • 多窗口断线后自动晋升
可扩展性
  • 13 个模块化工具集，独立可扩展
  • 动态工具注册（YAML + builtInToolsMap）
  • Client Bridge 机制支持远程扩展

潜在改进方向

领域 现状 改进建议
请求-响应关联 MCPServerManager 的 ClaudeMCP 模式缺乏可靠的 request-response 映射 引入 pendingRequests Map 模式（类似主进程已有实现）
工具定义统一 parameters / inputSchema 命名不一致，需要运行时转换 全量迁移到 MCP 标准的 inputSchema 字段
错误传播 ChatManager 委派失败后 rethrow 而非 fallback 对特定错误类型（如"工具未注册"）尝试 fallback handler
WebSocket 消息协议 内部 WS 消息格式与 MCP JSON-RPC 不完全对齐 统一内部通信也使用 JSON-RPC 2.0 格式
Client Bridge 轮询式（bridge 客户端需主动 poll），且桥接选择策略为 TODO 实现 WebSocket 推送式 bridge + 多 bridge 负载均衡
类型安全 纯 JavaScript，无编译时类型检查 考虑 TypeScript 化关键路径（ToolsIntegrator、IPC 消息类型）
性能可观测性 console.log 为主，缺少结构化日志和指标 集成 OpenTelemetry 或结构化日志框架
